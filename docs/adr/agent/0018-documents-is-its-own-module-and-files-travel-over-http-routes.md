# Documents is its own module, and files travel over HTTP routes, not MCP

Ticket #21 of spec #20 adds the Documents package (schema `documents`, own migrations, listed in `allMigrations`). It imports no other domain module. The API depends on it through the `documents` field of the tool dependencies, which is required (the worker's `composeApp` also builds it, so the end-to-end test wires the same object).

Files do not travel through MCP, because the endpoint caps bodies at 1 MiB and a model cannot write binary reliably. `POST /files?kind=&filename=` (raw body) and `GET /files/<id>` sit next to `/mcp` and use the same bearer check; unknown paths still answer 404 before the check. `kind` is master_resume, master_cover_letter or photo. The bytes live in their own table (`file_bytes`) so listings never read them. A new upload never removes an older one, and `register_master_document` only moves the pointer (`master_documents`, one row per user and kind).

The type is decided from the content, never the declared type or the file name: PDF by its magic bytes, DOCX as a zip whose entry names contain `word/document.xml`, Markdown and text as valid UTF-8 without NUL bytes (Markdown only tells itself from text by the `.md` name, which only picks the label), PNG and JPEG by magic bytes for the photo. A Master file never accepts an image and a photo never accepts anything else. The limit is 10 MB: a declared length over it is answered 413 before any byte is buffered (the rest of the body is drained to nowhere so the client can read the answer), and a body without a length is counted while it is read and cut off at the limit. Another user's file id and an unknown id are the same 404 on the route and the same refusal text in the tool.

Career bank items are rows in one table (`career_items`: kind, optional parent, position, jsonb value). Each kind has one zod schema (`workExperienceValue`, `experiencePointValue`) that the import, the MCP output and the stored value are all parsed with, with the caps in `CAREER_LIMITS`. Every write also appends a row to `career_revisions` (old value, new value, reason, actor) in the same transaction; this ticket writes only reason import by actor skill. There is no hidden flag yet: hide and restore arrive with their own ticket and add it by migration.

`save_career_bank` adds after the existing Work experiences and is not a replace: positions continue from the highest stored one under a per-user advisory lock, so two imports never share a position. Importing the same resume twice stores it twice; the skill says so. `get_career_bank` also returns the two current Master files, so a registration can be read back.
