# Review is its own module, and the creating module applies decisions

Review is a package with schema `review` and no dependency on another domain module. An item has a user id, a kind (`ai_merge`, `ai_fit_rejection`, `mail_match`; only the second is raised so far), a subject (ids of the other module's rows, for an AI fit rejection the Job and the Target), the model that made the call (the model the runner reported, not the configured one), a status (pending, confirmed, disagreed) and created and decided times. A unique index on user, kind and subject allows one item per question, so two workers raising the same one create it once, and `create` returns `created: false` for the second. Review stores items and decisions and counts agreement (confirmed is agreed, disagreed is disagreed, pending is not counted) per kind and model, plus the confirmed items as "survived". Every query is scoped by user id.

Matching raises an `ai_fit_rejection` item in the same transaction that stores a score below the threshold in force at scoring time (the Target's, then the Global default, then the configured one; 0 is real), so a crash cannot leave a rejected pair without its item and a pair is never scored twice. Editing criteria does not rescore (ADR 0011), so it raises no duplicate, and a later threshold edit raises none either: items exist only for scores that landed below the threshold when they were made. The Run counts the items it created (`ai_rejections`).

The creating module applies a decision. `decide` in Review takes the item row lock, checks it is pending, calls an applier the caller supplies with the item and the same transaction, then writes the decision. A failing applier rolls everything back and leaves the item pending; two concurrent decisions of one item cannot both apply; deciding twice is refused. The API layer maps kind to applier, so an unknown kind fails clearly (`ai_merge` and `mail_match` appliers come with their tickets) and Review never imports another module. Confirm for an AI fit rejection changes nothing. Disagree makes Matching insert a row in `matching.tag_overrides` (unique per Target and Job, with a timestamp so the digest can find Jobs that gained a tag). Tagged is now the score at or above the current threshold, or an override. The override is Matching's own table, so the tag stays after a threshold edit. Matching refuses a subject whose Target is not the user's.

`list_reviews` reads posting links from Discovery and the Target name, score, reasons and red flags from `listScores` in the API layer, so Review stores no copy. If an edit of the Target dropped the Job from its candidates, the item still lists its posting links but shows no Target and score. `review_stats` also returns the pending count.
