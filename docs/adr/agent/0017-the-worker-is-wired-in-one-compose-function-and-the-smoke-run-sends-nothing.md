# The worker is wired in one compose function, and the smoke run sends nothing

`composeApp` (`apps/worker/src/compose.ts`) migrates, seeds the user and builds every module from the validated config. `main.ts`, the end-to-end test and the smoke script all call it, so the test exercises the wiring the process runs, not a copy. Its one test hook is an optional `fetch` that replaces the HTTP of the sources, the OpenRouter runner, Gmail and the webhook together; unset means the real network. The `claude -p` runner (a child process) and Redis are not covered by it. The API process keeps its own smaller wiring, since it never polls.

The skill file `skills/job-hunter/SKILL.md` lives in the repo and is checked by the end-to-end test against the tool list the MCP server reports, so a new tool without a skill entry fails the suite. Linking it into the user's skills folder is a documented one-line command, not something a test or script does.

The smoke script runs one live cycle for the configured user: every scheduled source once, then the AI totals. It never polls Gmail: a poll claims each real reply in the processed-mail ledger and changes real statuses, and with notifications off the Telegram line would be lost for good. Its Jobs and scores stay in the database, so they appear in the next real digest. It is manual only (no workflow references it, and it refuses when NODE_ENV is test or CI is set). It switches notifications off, so no digest or alert reaches Telegram, and prints counts and cost, never settings. It still writes to the configured database like a normal run and spends AI calls, which is its point. Its refusal rule is the only unit tested part; the rest is wiring, excluded from the coverage gate like `main.ts`.
