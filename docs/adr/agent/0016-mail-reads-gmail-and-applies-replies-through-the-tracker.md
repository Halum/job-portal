# Mail reads Gmail over HTTP and applies replies through the Tracker, claiming each mail in a ledger first

Mail is a package with schema `mail` (processed-mail ledger, unmatched mails, the pending detail of mail_match items, the poll cursor). It reads other modules only through exported functions handed to `createMail`: Tracker (`findJobIds`, `setApplicationStatus`, `addNote`), Discovery (`getJob`), Review (`create`), AI (`run`, feature `mail_classify`) and Notifications (`sendLines`, `setFailure`). Gmail is called with `fetch` (read-only scope, OAuth refresh token, access token kept in memory and renewed a minute early), so there is no googleapis dependency; the client id, secret and refresh token are env only, all three or none. Without Gmail credentials or an AI runner the poll is skipped with one log line.

A mail is claimed before anything is applied: one transaction inserts the ledger row (unique per user and message id), then applies the change under the Job row lock, so a replayed mail or a second worker finds the row and does nothing, and the ledger row and the Timeline event commit or roll back together. The Tracker's `setApplicationStatus` and `addNote` therefore take an optional caller transaction (the same lock order as ADR 0007: ledger insert, then Job lock). A poll also holds a lease on the user's cursor row (ten minutes, taken with one conditional update), so two workers do not pay for the same AI calls; the ledger, not the lease, is what keeps the result correct. The cursor moves only after a pass that finished, to one hour before the pass started, so a mail that reached the inbox late is still listed and the ledger skips the rest.

Candidates are the user's Jobs with an application status other than Accepted, Declined or Withdrawn (so Rejected and Gone cold still get mail; a Job Discovery hides is skipped). Narrowing is code, not AI: the sender's domain against the company name and the posting hosts, the company name in the display name, subject and cleaned body (at least four letters, legal suffixes dropped), and for a known ATS sender the company name first, then Jobs posted on an ATS host; at most ten candidates. No candidates and a mail that is not job-like (job words, or an ATS sender) leaves a ledger row only; job-like with no candidates is stored as unmatched without an AI call. The AI sees subject and body with quoted replies, the reply header and the signature removed, capped at 4000 characters, no attachments, inside one JSON value with "<" escaped, and answers kind, one candidate id or null, confidence and a one-sentence summary; an id that is no candidate counts as null. A runner-wide AI failure (key, cap, network) stops the pass and leaves the rest for the next poll; a bad answer or rejected request stores that mail as unmatched so it is never lost; `AI_MAIL_MAX_CALLS_PER_RUN` bounds the calls of one poll.

A clear match (a Job and high confidence) applies at once: rejection, screening, interview and offer set Rejected, Screening, Interview and Offer as actor gmail with evidence `gmail:<message id>`, then one Telegram line goes out after the commit; an acknowledgement is a Timeline note only (not an event, so it does not reset the Gone cold clock) and Applied is never set by Gmail. A change the state model refuses (a final status, a backward move) is recorded as a note with the reason, never thrown away. A low-confidence pick becomes a `mail_match` Review item (subject: the message id; the mail summary, sender, subject and candidates sit in `mail.matches`); confirm applies the mail to the Job the AI picked in the decision's own transaction (ADR 0012, so `ReviewTx` is now the full `DbTx`) and disagree records only the decision. A kind `other` mail leaves a ledger row; a kind with no Job is unmatched and listed by `list_unmatched_mails`.

Notifications gained `setFailure(userId, key, failing)` for the `gmail_token` failure type outside a run: a refused refresh token or a 401 that survives one renewal opens it (one alert) and the next good poll closes it (one recovery); an outage or rate limit is not a token failure and only logs. Gmail status changes use `sendLines` (message kind `line`).

Known looseness, accepted: a Telegram line is sent after the commit, so a crash between loses it; the Job is chosen from the candidates loaded at the start of a pass, so a status change in the middle shows up as a note, not a wrong write; an AI runner that is down is only logged by Mail, not alerted (the Pipeline's `ai:` failure types observe scoring and merge calls).
