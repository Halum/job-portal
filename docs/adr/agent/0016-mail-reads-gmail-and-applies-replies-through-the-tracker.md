# Mail reads Gmail over HTTP and applies replies through the Tracker, claiming each mail in a ledger first

Mail is a package with schema `mail` (processed-mail ledger, unmatched mails, the pending detail of mail_match items, the poll cursor). It reads other modules only through exported functions handed to `createMail`: Tracker (`findJobIds`, `setApplicationStatus`, `addNote`), Discovery (`getJob`), Review (`create`), AI (`run`, feature `mail_classify`) and Notifications (`sendLines`, `setFailure`). Gmail is called with `fetch` (read-only scope, OAuth refresh token, access token kept in memory and renewed a minute early), so there is no googleapis dependency; the client id, secret and refresh token are env only, all three or none. Without Gmail credentials or an AI runner the poll is skipped with one log line.

A mail is claimed before anything is applied: one transaction inserts the ledger row (unique per user and message id), then applies the change under the Job row lock, so a replayed mail or a second worker finds the row and does nothing, and the ledger row and the Timeline event commit or roll back together. The Tracker's `setApplicationStatus` and `addNote` therefore take an optional caller transaction (lock order: the ledger insert first, then the Job row lock, always, so a replay and a set_status never wait on each other in a cycle). A poll also holds a lease on the user's cursor row (ten minutes, taken with one conditional update that stores a lease token, renewed after every mail and released only by its own token), so two workers do not pay for the same AI calls and a slow worker cannot release a lease it lost; the ledger, not the lease, is what keeps the result correct. Mails are handled oldest first. The pass first lists every id of the window (ids are cheap): when the page cap truncates a list, the next list starts below the oldest id seen, known ids included, until the list ends, then the ids not in the ledger are handled oldest first, up to the call cap. A backlog is therefore finished over several polls and a poll never stalls on mail that is already handled. A page or mail Gmail fails to serve is logged and skipped, the rest goes on, and the cursor stays put so the next poll retries it; only a refused token stops the pass. The cursor moves only after a pass that finished, to one hour before the pass started, so a mail that reached the inbox late is still listed and the ledger skips the rest. Gmail errors: a 401 triggers one token refresh and one retry, a second 401 is an auth error; a 403 is an auth error unless the body names a rate, daily or quota limit; a token endpoint 400 is an auth error only for invalid_grant, invalid_client or unauthorized_client.

Reply candidates are the user's Jobs with an application status other than Accepted, Declined or Withdrawn (so Rejected and Gone cold still get mail; a Job Discovery hides is skipped). Narrowing is code, not AI: the sender's domain against the company name and the posting hosts, the company name in the display name, subject and cleaned body (at least four letters, legal suffixes dropped), and for a known ATS sender the company name first, then Jobs posted on an ATS host; at most ten candidates. No candidates and a mail that is not job-like (job words, or an ATS sender) leaves a ledger row only; job-like with no candidates is stored as unmatched without an AI call. The AI sees subject and body with quoted replies, the reply header and the signature removed, capped at 4000 characters, no attachments, and only the sender's domain (never the display name or address), inside one JSON value with "<" escaped (the mail text is untrusted and may carry instructions), and answers kind, one candidate id or null, confidence and a one-sentence summary; an id that is no candidate counts as null. A runner-wide AI failure (key, cap, network) stops the pass and leaves the rest for the next poll; a bad answer or rejected request stores that mail as unmatched so it is never lost; `AI_MAIL_MAX_CALLS_PER_RUN` bounds the calls of one poll.

A clear match is decided in code, not by the AI alone. Trust rule: the sender is the From address (the part inside `<...>`, never the display name) and its domain equals, or is a subdomain of, the domain of a non-ATS posting host the Job holds (last two labels, three under a country second level such as co.uk); and the topmost Authentication-Results header, added by mx.google.com, has a clause that starts with `dkim=pass` whose `header.d` (else `header.i=@domain`) is that domain or a parent of the sender's domain. The header is read clause by clause, so the envelope sender copied into the spf clause or any other text an outside sender controls never counts. On top of that exactly one narrowed Reply candidate must remain, the AI's confidence must be high and its pick must be that candidate. Only then the mail applies at once; an ATS sender, a name in the text only, a lookalike domain, a forged display name or a missing or unparseable header never does and becomes a `mail_match` Review item instead. An applied mail: rejection, screening, interview and offer set Rejected, Screening, Interview and Offer as actor gmail with evidence `gmail:<message id>`, then one Telegram line goes out after the commit; an acknowledgement is a Timeline note only (not an event, so it does not reset the Gone cold clock) and Applied is never set by Gmail. A change the state model refuses (a final status, a backward move) is recorded as a note with the reason, never thrown away. A `mail_match` Review item (subject: the message id; the mail summary, sender, subject, kind, the AI's suggested Job and the `possibleJobIds` sit in `mail.matches`) is decided with `decide_review`: confirm without `jobId` applies the AI's suggestion, confirm with `jobId` applies that Job, which must be one of `possibleJobIds` (anything else is refused and the item stays pending), and `jobId` on any other kind, or with a disagree, is refused as an invalid argument; disagree records only the decision. The apply runs in the decision's own transaction (ADR 0012, so `ReviewTx` is now the full `DbTx`). The ledger outcome of a mail is applied, noted, ignored, unmatched, review or disagreed; `applyMatch` settles a review row to applied, noted or disagreed. A kind `other` mail leaves a ledger row; a kind with no Job is unmatched and listed by `list_unmatched_mails`.

Notifications gained `setFailure(userId, key, failing)` for the `gmail_token` failure type outside a run: a refused refresh token or a 401 that survives one renewal opens it (one alert) and the next good poll closes it (one recovery); an outage or rate limit is not a token failure and only logs. Gmail status changes use `sendLines` (message kind `line`).

Known looseness, accepted: a Telegram line is sent after the commit, so a crash between loses it; the Job is chosen from the candidates loaded at the start of a pass, so a status change in the middle shows up as a note, not a wrong write; an AI runner that is down is only logged by Mail and leaves the mails for the next poll; no `ai:` failure type is opened for it (the Pipeline's `ai:` failure types observe scoring and merge calls only).
