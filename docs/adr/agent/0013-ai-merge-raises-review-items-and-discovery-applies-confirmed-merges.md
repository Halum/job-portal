# AI merge asks about near duplicates, raises Review items, and Discovery applies a confirmed merge

AI merge lives in Discovery (`createAiMerge`), which depends on the AI runner and Review packages (neither imports Discovery). It runs in the Pipeline after Matching and before scoring, over every mergeable Job of the user (New or Shortlisted, with no application status through the injected `hasApplication`), not only the Jobs of the run, so a pair whose call failed is asked again by the next run of any source.

Candidate pairs, both read from Discovery's own tables: near matches (same normalized company and city, title word Jaccard at or above `AI_MERGE_JACCARD`, default 0.6; `nearBucket` and `titleOverlap` in `keys.ts`) and `merge_conflicts` rows (the Jobs the keys hit, resolved to the Job they were folded into). A pair is skipped when a never-merge pair covers it (a Posting of one Job is barred from the other, seen through Jobs folded into either), when an ai_merge Review item exists for it in any status, or when an earlier answer said it is not the same job. The last one is a deviation from the ticket text (which stored nothing for a "not the same" answer): without it every run would ask, and pay for, the same pairs again. It is the table `discovery.merge_checks` (unique per user and Job pair, smaller id first); the call log still holds the call.

The call goes through `Ai.run` with the feature name `ai_merge` (logged, cost kept, runner-wide failures end the pass after three in a row, a bad answer for one pair does not). It has its own cap, `AI_MERGE_MAX_CALLS_PER_RUN` (default 20), separate from `AI_MAX_CALLS_PER_RUN`: a throughput limit, not a spend cap, the pairs left over wait for the next run. The run's `aiCalls` and `aiCostUsd` add both kinds together; `aiMergeItems` counts the items the run created. One Postgres advisory lock per pair (taken with try-lock, held through the AI call, released with the transaction) keeps two workers from asking the same pair; the item and the check marker are written in that transaction, and the unique index on the item is the last guard. The item subject is `{ jobA, jobB }` with the smaller id first, so one pair is one item in either order. The item records the model the runner reported.

Nothing merges until the user confirms. Review's `decide` calls the applier the API maps to the kind (`aiMerge.apply`), in the decision's transaction. Disagree writes a never-merge pair for every Posting of each Job against the other Job, so the pair is never asked again. Confirm locks both Job rows in id order and folds the newer Job into the older one: its Postings move to the older Job and its row stays with `merged_into` set, keeping its company and URL keys. A later Posting that hits a folded Job's key is attached to the Job it was folded into (Discovery resolves `merged_into`), which closes the URL key chain from the #9 review without a key table: the older Job may hold only one URL key, the folded one keeps the other as an alias. Ingest takes a share lock on the Jobs its keys hit, so it waits for a merge that is moving them and then sees the result; a Posting is never left on a folded Job. Folded Jobs are hidden from `listJobs`, `getJob`, `listMatchable` and `splitJob`.

Confirm is refused with a Discovery error, and the item stays pending (the user can disagree), when either Job has an application status, is Dismissed or Expired, or a split since the proposal bars the pair. A Job missing for the user, or two ids that already resolve to one Job (an earlier confirm folded them), is a no-op that still records the decision. The kept Job is the older one (by creation time, then id) and keeps its Tracker state, Timeline events, notes and discovery state. The folded Job's Tracker, Timeline, notes, candidates and scores are not moved or deleted (modules never write each other's tables): they stay under its id, and because the Job is hidden they are unreachable and Matching never scores it again; since a Job with an application is never merged, no application is lost. A pending item that names a folded Job stays pending until decided; its Postings now show under the Job it went into.

`list_reviews` shows the Postings of both Jobs for an ai_merge item, `decide_review` applies it, and `review_stats` groups it by kind and model like the others.
