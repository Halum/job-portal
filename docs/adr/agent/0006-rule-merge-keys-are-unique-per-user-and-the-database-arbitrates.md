# Rule merge keys are unique per user, and the database settles races

Supersedes 0003 (one Job per Posting). A Job carries a company key (normalized company with legal suffix stripped, normalized title without bracketed gender tags, and city, only when all three are present) and a URL key (the URL without scheme, www, fragment, tracking parameters and trailing slash, parameters sorted). Both are nullable, with a unique constraint on (user, company key) and on (user, URL key). A new Posting that matches exactly one Job through either key attaches to it; otherwise it creates a Job holding its keys. A Job's keys are the ones of the Posting that created it and are not updated when later Postings attach.

Each Posting is ingested in its own short transaction. A Job insert that loses a race on a key does nothing, and the loop reselects and attaches to the winner, so concurrent runs and several workers cannot create duplicate Jobs and never wait on a lock held across a whole poll. A spare Job created for a Posting that a concurrent run inserted first is deleted again.

When the two keys hit different Jobs nothing merges: the Posting gets its own Job with null keys, and the pair of Jobs is stored in `discovery.merge_conflicts` for the AI merge ticket (`listMergeConflicts` is the stub list). A split moves chosen Postings into a new Job with null keys (the original Job keeps its keys and at least one Posting), writes a never-merge pair (Posting, original Job) per Posting and one `splits` row, whose count is the split count. A Posting is only matched when it is new, so a split Posting is not re-merged by the next run; the never-merge pairs are for the AI merge ticket, which can propose merges for existing Postings.

Jobs have a `discovery_state` column (new, shortlisted, dismissed, expired). A Dismissed Job keeps its keys, so a matching Posting attaches to it instead of creating a visible Job. Changing the state is the status ticket's work. `add_job` is a Posting with source `manual` whose source posting id is the URL key, so adding the same URL again is a no-op and a board copy merges through the normal keys.

Normalization, as fixed after the first review: the fold maps the sharp s to ss, writes C++ as "c plus plus" and C# as "c sharp" so they stay apart from plain C, and reads "e.V." (also "e. V." and "EV") as a legal suffix. The gender marker is removed in bracketed form and as an unbracketed "m/w/d" in any order and case, with spaces around the slashes allowed. A leading five digit postcode is dropped from the city ("96047 Bamberg" is "Bamberg"); a trailing one is kept. Stored keys are not backfilled when these rules change: no automation database holds real data yet, so local scratch databases are wiped, and a Job created under older rules keeps its older keys (a later Posting that would match only under the new rules does not merge into it).

A poll stores a Posting the database refuses (Postgres class 22 data exception or class 23 constraint violation, or a Discovery refusal) as one short error line and logs the cause through the shared logger. Any other error, such as a lost connection, is rethrown so the run ends failed, not completed with errors.
