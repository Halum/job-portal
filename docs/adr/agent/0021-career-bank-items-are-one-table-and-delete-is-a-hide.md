# Career bank items are one table with one schema per kind, and delete is a hide

Ticket #22 of spec #20 adds the rest of the Career bank. All seven item kinds (work_experience, experience_point, resume_entry, outline_section, cover_letter_paragraph, writing_style, contact) live in `career_items`, as ADR 0018 started. Each kind has one zod schema in `src/documents.ts` (`VALUE_SCHEMAS`); the import, `upsert_career_item` and a restore parse with it, and `get_career_bank` parses stored values with it (the write tools return the value as stored, and revision values are history, not parsed on read). A Resume entry is a discriminated union on its own `kind` (education, skill, language, certificate).

The parent of an Experience point is a Work experience and the parent of a Cover letter paragraph is an outline section. A parent id is looked up by user, id and kind, so another user's id, an unknown id and a parent of the wrong kind all give the same `not_found` text. A parent cannot be changed by an edit. The Writing style and the contact details are singletons (a partial unique index on user and kind): a write to them updates the one stored, whether or not an item id is given. The contact photo is a file id; it must be the user's own upload of kind photo.

Delete is a hide: `career_items.hidden`, plus a revision with reason hide. Hiding an already hidden item and hiding a singleton are refused. `get_career_bank` lists hidden items marked `hidden: true`, so the user can see and restore them; the Target resolution of ticket #23 drops them. An Experience point or paragraph cannot be added under a hidden parent. Hiding a parent does not change its children's flag; resolution (#23) must treat the children of a hidden item as hidden. A hide revision has the same old and new value, so the hidden state is only in its reason; restoring by the id of a hide revision therefore unhides the item with unchanged text.

Restore has two forms. Without a revision id it unhides. With a revision id (of the same item and user) it sets the item to that revision's new value and unhides it. Both write a revision with reason restore, so history only grows. Reasons are import, coaching, enrichment, user_edit, hide and restore; `upsert_career_item` takes only the middle three. The actor is user or skill and defaults to skill at the tool.

Every write takes the per-user advisory lock, so a position is assigned without gaps or duplicates (per user, kind and parent). `save_career_bank` now takes any part of the Master files (all optional, not all empty) and is still an add, not a replace; its output counts every part. `listRevisions` refuses an item that is not the user's instead of returning an empty list.
