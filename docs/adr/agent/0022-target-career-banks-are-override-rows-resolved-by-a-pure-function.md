# Target career banks are override rows resolved by a pure function

Ticket #23 of spec #20 gives each Target its own view of the Career bank without copying it. A Target has no stored bank: it has Career bank overrides (`career_overrides`: user, Target id, action hide / replace / add, item kind, item id for hide and replace, parent id for an add, the typed value, the revision a replace was made against). `resolveCareerBank` (`src/resolve.ts`) is pure: it starts from the Career bank without its own hidden items, marks the items a Target hides, swaps in replacements, and appends Target-only additions in creation order. Every item comes back marked inherited, replaced, added or hidden, with the id of the override that made it. Items the Career bank hid are left out; items a Target hides stay in the view marked hidden, with everything that hangs under them, so the user can see and clear them (the consumer uses only the items that are not hidden). Later Career bank edits show through every inherited item, so a fact is fixed once.

The value of a replace or an add is parsed by the item kind's existing zod schema (`parseValue`), and a replace holds the whole item value, as ADR 0021 settled. Overrides cover Work experiences, Experience points, Resume entries and Cover letter paragraphs (the kinds named in the user stories). Outline sections, the Writing style and the contact details are not overridable, and the tools refuse them. A hide or replace is at most one row per Target and item (partial unique index): setting an item again changes that row in place and keeps its id. An add names its parent: a Career bank item of the parent kind, or, for an Experience point, a Work experience the same Target added, so a Target-only Work experience can have points. Clearing a Target-only Work experience also clears the points added under it, each with its own revision.

Revisions: every set, change and clear writes a row to `career_revisions` with item kind `override` and the override id as the item id (the check constraint on the item kind gained that value). Old and new value are a snapshot of the override (Target, action, item kind, item id, parent id, value). A set or change carries the caller's reason (coaching, enrichment, user_edit); a clear has reason restore and the new value `{"cleared": true}`, because the override row itself is deleted and the history lives in the revisions. `listRevisions` accepts an override id: it refuses an id that has no revision of the user's, which is every unknown or foreign id.

Stale replacements: a replace stores the item's newest revision id at the time. When the item's newest revision is a different one, the resolved view marks the replacement `stale` and still shows the Target text (the Target's replaced text wins), and the skill tells the user the Career bank version changed and offers to update the Target. Setting the replacement again makes it current. Any newer revision counts, including a hide and a restore of the item, even when its text did not change.

Target ids are checked through an injected lookup, `hasTarget(userId, targetId)`, the second argument of `createDocuments` (ADR 0009 style, Documents imports no domain module). `apps/api/src/main.ts` and the worker's `composeApp` build it from Matching's `listTargets`, so Matching needs no new export. Without a lookup every Target call is refused as not_found, which is also the answer for an unknown and for another user's Target. A cleared override is found by user and id only, because its Target may be gone.

MCP: `set_career_override`, `clear_career_override`, and an optional `targetId` on `get_career_bank`, whose output then carries `source`, `overrideId` and `stale` on each item.
