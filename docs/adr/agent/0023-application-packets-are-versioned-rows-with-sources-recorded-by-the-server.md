# Application packets are versioned rows with sources recorded by the server

Ticket #25 of spec #20 stores each preparation for a Job as an Application packet (`application_packets`: user, Job id, Target id, version, the resume and letter content, the sources, the Requirement gaps, the Enrichment questions asked, both PDF file ids, page counts, over-cap flags, the sent mark). The rows are never edited except for the sent mark: preparing again adds a version.

Sources. The content shapes of #24 (`resumeContent`, `letterContent`) stay untouched, so sources travel beside them in one parallel structure (`packetSources`) with the same order and lengths: per Work experience and per Experience point, per education, skill, language and certificate entry, and per letter paragraph. A mismatch in counts is refused. Callers pass only item ids, the ones `get_career_bank` with a `targetId` shows (a Career bank item id, or the override id of an item the Target added). The server resolves the Target career bank, refuses every id that is not in it (unknown, another user's, hidden for the Target or under a hidden parent, all the same not_found) and stores for each source the item id, its kind, whether the Target saw it inherited, replaced or added, the newest revision id of the item (of the override for an added one), the override id and, for a replaced item, the newest revision of the override itself (`overrideRevisionId`, so the wording used stays identifiable). A merged line lists several sources. A letter paragraph drafted because nothing fit has no ids and `isNew` true; any other line without a source is refused. The kind of each cited item is not checked against the line (a Why-me paragraph legitimately cites Experience points).

Versions. The next version is `max + 1` read under a transaction advisory lock on the user's packets of that Job, and the unique index (user, Job, version) backs it. A partial unique index allows one sent version per Job; `mark_packet_sent` clears the old mark and sets the new one in one transaction under the same lock, and an unknown version rolls the clearing back. Rendering happens before the transaction, so the lock is held for the inserts only.

PDFs. The two PDFs are rows of `files` with the new kinds `resume_pdf` and `letter_pdf`, which the check constraint allows but the upload route does not (`FILE_KINDS` is still the upload list), so the existing `GET /files/<id>` serves them. The photo of the Target's contact details is passed to the resume renderer when it has one.

Lookups. A Job is checked through the injected `hasJob` of `createDocuments(db, deps)` (the API and `composeApp` build it from Discovery's `getJob`), like `hasTarget`; without it every packet call is refused. A Job that is not the user's is refused on every tool, including list and get. `get_job` gets a `packets` summary (count, newest version, sent version), assembled in the API from `packetsOverview` after the Job itself was found.
