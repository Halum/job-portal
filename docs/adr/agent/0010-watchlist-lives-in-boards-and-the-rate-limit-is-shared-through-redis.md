# The Watchlist lives in the boards module, and the per-host rate limit is shared through Redis

The Watchlist is per user, the Board directory is shared, and both are read together to decide which boards a run fetches. They stay one module: the Watchlist is a second table in the `boards` schema (unique per user, ats and token, no foreign key to the directory), so `listBoards(userId, ats)` can join the two without one module querying another's schema. Discovery stays unaware: the worker injects `watchlist.listBoards(user.id, ats)` as the ATS source's `listBoards`. An empty Watchlist (across all ATSs, not per ATS) means every marked board; a non-empty one means only watched boards, so watching one Greenhouse board stops Lever and Ashby fetching until the Watchlist is empty again. A watched board that is not marked is still not fetched. `update_watchlist` only accepts boards already in the directory and writes nothing when one is unknown.

`add_board` puts the new board on the Watchlist as the spec says, so adding one board to an empty Watchlist narrows every run to that board. The tool description says so. The URL parsing (`resolveBoardUrl`, exact host match, https only, no credentials) sits in Discovery beside the ATS adapters. The one verification fetch is `fetchBoardPostings`, so a failing board changes nothing. The directory name is the first posting's company, else the board id (Lever and Ashby give none).

Board ids from user input are validated once, in `fetchBoardPostings`, with `/^[A-Za-z0-9._-]+$/` and "." and ".." refused, because `encodeURIComponent` leaves dots alone and `..` would climb out of the ATS path. Every caller (sources, the mark script, add_board) routes through it.

The rate limit moved from a per-process slot map to a `SlotStore`: in memory by default, Redis for the worker, the API and `boards:mark`. One Lua step on Redis's own clock books the next free slot per host (a token bucket with no burst, gap rounded up to whole ms so the real rate is at or under the configured one). A two-process test proves two workers together stay under `BOARD_REQUESTS_PER_SECOND` and that the same test fails with per-process slots. If Redis is down a request fails and shows as a board error line, rather than going out unpaced.

Review round 1 added these decisions:

- **add_board writes the shared directory.** The Board directory has no user id, so a board added by one user is marked for everyone's runs when their Watchlist is empty. This follows the spec ("adds it to the directory (marked)") and is accepted: the directory is public company data, and the user's own Watchlist is what narrows their runs. The directory row and the watch are written in one transaction (`watchlist.addMarkedBoard`), and a re-add updates the board's host (Lever EU versus US) but never its name. The result says when the Watchlist went from empty to non-empty (`narrowedWatchlist` and a note), because that narrows every ATS.
- **Tool errors never carry driver text.** Errors written for the user (`DiscoveryError`, `BoardsError`, `BoardFetchError`, `RateLimitError`) pass their message through; anything else (Drizzle, ioredis, network) is logged with its cause and shown as a fixed text.
- **Redis is bounded.** A slot reservation whose wait would pass 30 s is refused and not booked, so a flood of add_board calls cannot push every worker's fetches far into the future. add_board is also limited to 10 attempts per user per hour, counted on Redis before the verification fetch (so a loop of bad boards is limited too). Board tokens, update_watchlist lists and the URL have maximum lengths (100, 100 per list, 2048).
- **A down Redis fails fast.** The limiter's client gives up a command after one retry and logs its connection errors; the request, or the add_board call, fails with "rate limit store unavailable" and nothing is sent. Every process gets the client through `connectRateLimiter`, and the API closes it on shutdown.
- **Board fetches never follow redirects**, `add_board` has no unthrottled fetch default, and the legacy EU Greenhouse host (boards.eu.greenhouse.io) is accepted by the resolver.
