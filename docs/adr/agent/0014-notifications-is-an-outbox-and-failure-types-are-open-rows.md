# Notifications is an outbox, and failure types are open rows

Notifications is a package with schema `notifications` and no dependency on another domain module. It is handed what it reads as functions (new tags from Matching's `listNewTags`, Job title and links from Discovery's `getJob`, the waiting count from Review's `countPending`), wired in `apps/worker/src/notifications.ts`. The Pipeline calls `afterRun` last, after scoring, with the run's start, the failure types failing now and the types the run could observe. A crash there is an error line on the run, never a failed run.

Every message is stored first, in `messages` (kind digest or alert, payload, status pending, sent or folded, attempts), then sent. A send retries inside the run with a doubling backoff (`NOTIFY_MAX_ATTEMPTS`, default 3; `NOTIFY_BACKOFF_MS`, default 1000); a 4xx other than 408 and 429 is about that message and is not retried. A message still failing stays pending. Alerts are sent before digests and each kind oldest first. A rejected message (4xx) stays pending and the pass goes on; a webhook that is down (5xx, network, timeout) ends the pass, so order is kept and nothing waits behind a rejected digest. The next run that finds new pairs folds every pending digest message into one new set: the entries are pooled and split again; with nothing new, pending digest messages are sent as they are. The webhook URL and the topic id come from env only, together or not at all (setting one stops the process at start); unset means the step is skipped with one log line. The URL is never logged or put in an error.

A digest is split into as many messages as needed to stay under 3900 characters (Telegram caps at 4096): whole Job blocks, best score first, each message its own outbox row, "part i of k" in the header when k is more than 1, the Review count on the last. A Job too long for one message loses its reasons first (links stay) and is clipped as the last resort; title, company, Target name, reasons and links are clipped per field. Each message is sent and counted on its own, so a message that got a 2xx is never sent again and the others wait.

New tags are looked up from a per-user watermark (`watermarks`): Matching's `listNewTags` returns the pairs tagged now that were scored at or after it, plus every tag override whatever its date. The watermark starts at the first run's start and moves only after the digest is stored, to the database clock minus one hour, because a scoring transaction can stamp a score earlier than it commits and the overlap costs only a rescan. A crash or failure before the digest is stored therefore lists the same pairs on the next run. `digest_pairs` (unique per user, Job and Target) is claimed in the same transaction that stores the digest rows, so a pair is listed once ever and two workers finishing runs at once list it once: only the insert that wins lists the pair. A pair whose Job is Dismissed or Expired when it is looked at is skipped for good, unless the user later overrides its tag (overrides are looked up whatever their date). Digests are cut only by the length rule above, never by a count of Jobs.

A failure type is a key (`source:<id>`, `board:<ats>:<token>`, `ai:<runner>:<class>`, `webhook`; the key space is open for the Gmail token). `open_failures` holds the types failing now, unique per user and key: the insert that creates a row queues the "Failing" alert and the delete that removes it queues the "Recovered" alert, each in one transaction with its row, so each fires once however many workers race. A run closes only the types it checked: a failed run checks only its source; a run checks its own source's boards (`board:<source>:`) and checks AI types (`ai:`) only when it made calls. The Pipeline derives the keys from the stable error lines of Discovery (a failing board) and Matching (a failed call with its class), so those formats are now an interface. A webhook that stays down after the retries opens `webhook`; its alert waits in the outbox and goes out with the recovery notice once a send lands.

A send holds the message row lock (`FOR UPDATE SKIP LOCKED`) through its retries, like a scoring pass, so two workers never send one message twice; it holds one connection per send in flight, up to about 33 seconds at the defaults (ponytail: move the send out of the transaction with a lease column before running many workers).

Known looseness, accepted: a board that left the Watchlist or lost its mark is covered by the checked prefix `board:<source>:` and is reported recovered; an AI class that succeeds closes another class while the runner is still failing for it (keys are per class); a scoring pass that throws as a whole is a "scoring failed" line that matches no failure type, so it opens no alert.
