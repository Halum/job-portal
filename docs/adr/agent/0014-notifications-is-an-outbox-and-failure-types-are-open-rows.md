# Notifications is an outbox, and failure types are open rows

Notifications is a package with schema `notifications` and no dependency on another domain module. It is handed what it reads as functions (new tags from Matching's `listNewTags`, Job title and links from Discovery's `getJob`, the waiting count from Review's `countPending`), wired in `apps/worker/src/notifications.ts`. The Pipeline calls `afterRun` last, after scoring, with the run's start, the failure types failing now and the types the run could observe. A crash there is an error line on the run, never a failed run.

Every message is stored first, in `messages` (kind digest or alert, payload, status pending, sent or folded, attempts), then sent. A send retries inside the run with a doubling backoff (`NOTIFY_MAX_ATTEMPTS`, default 3; `NOTIFY_BACKOFF_MS`, default 1000). A message still failing stays pending: the next run that finds new pairs stores one digest holding the earlier unsent entries and the new ones and marks the earlier digests folded; with nothing new, the next run sends the pending digest as it is. Pending messages go out oldest first and the pass stops at the first one the webhook refuses, so order is kept. The webhook URL and the topic id come from env only, together or not at all; unset means the step is skipped with one log line. The URL is never logged or put in an error.

A pair is new to a digest when Matching says it is tagged now and was scored at or after the run's start, or has a tag override (any date). `digest_pairs` (unique per user, Job and Target) is claimed in the same transaction that stores the digest, so a pair is listed once ever and two workers finishing runs at once list it once: only the insert that wins lists the pair. A pair whose Job is gone, Dismissed or Expired is not claimed and is listed later if the Job comes back. A digest line is one Job with a line per Target (score, reasons) and the posting links; the footer is the waiting Review count. Text is trimmed (three reasons, two links per Job) instead of split for Telegram's length cap.

A failure type is a key (`source:<id>`, `board:<ats>:<token>`, `ai:<runner>:<class>`, `webhook`; the key space is open for the Gmail token). `open_failures` holds the types failing now, unique per user and key: the insert that creates a row queues the "Failing" alert and the delete that removes it queues the "Recovered" alert, each in one transaction with its row, so each fires once however many workers race. A run closes only the types it checked: a failed run checks only its source; a run checks its own source's boards (`board:<source>:`) and checks AI types (`ai:`) only when it made calls. The Pipeline derives the keys from the stable error lines of Discovery (a failing board) and Matching (a failed call with its class), so those formats are now an interface. A webhook that stays down after the retries opens `webhook`; its alert waits in the outbox and goes out with the recovery notice once a send lands.

A send holds the message row lock (`FOR UPDATE SKIP LOCKED`) through its retries, like a scoring pass, so two workers never send one message twice; that holds one connection per send in flight.
