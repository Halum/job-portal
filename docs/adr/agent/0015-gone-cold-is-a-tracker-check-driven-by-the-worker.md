# Gone cold is a Tracker check driven by the worker, with N held in the Global defaults

The rule lives in `Tracker.goneCold(userId, { days, timezone })`: it takes the Jobs in Applied, Screening, Interview or Offer, finds each one's last Timeline event (any actor, undo events included, discovery-state events too, notes not; so a Gmail acknowledgement must stay a note, not a Timeline event, or it would reset the clock), and moves those whose last event is N or more calendar days old in the user's timezone to Gone cold with actor system and the rule as evidence. A day is a calendar date in that timezone, so a Job whose last event is on day D goes cold on day D+N whatever the hour. Each move is its own transaction that takes the Job row lock through Discovery and rechecks the status and the age inside the lock, so a set_status that wins the race leaves a fresh event and the check skips the Job; a Job folded into another by an AI merge has no lockable row and is skipped. A Job already Gone cold is not in the candidate set, so a re-run writes nothing. Tracker does not import Matching: the worker reads N and the user's timezone and passes them in.

N is `goneColdDays` in the Criteria schema, stored with the Global defaults (jsonb, so no migration): an integer of at least 1, null disables it, default null. It sits in the shared Criteria schema because that is where the defaults live; `upsertTarget` refuses it on a Target and `resolveCriteria` leaves it out (ponytail: a separate settings row if a second non-criteria setting appears). A change to the defaults rematches the Targets as any defaults change does, which is cheap and makes no AI call.

The Tracker's injected clock now also stamps Timeline events (`created_at`), not only `updated_at`, so tests control the age of an event. Production passes the real clock.

The worker schedules the check as one more BullMQ Job Scheduler (id and job name `gone-cold`, every `GONE_COLD_INTERVAL_MINUTES`, default 1440). The check is idempotent, so several workers or a repeated tick are harmless. After the moves, `createGoneColdCheck` (apps/worker) sends one short line per Job, "Gone cold: title at company, N days silent", through `Notifications.sendLines`: each line is its own outbox row of kind `line` (migration 0002 widens the kind check), sent with the same retries and webhook-down rule as every message and before any digest. No webhook configured means no lines and the move still happens; a failure to store or send a line is logged and never undoes a move. The move and the line are two transactions in two modules, so a crash between them loses that line (accepted: the status is the record, the line is a nudge).
