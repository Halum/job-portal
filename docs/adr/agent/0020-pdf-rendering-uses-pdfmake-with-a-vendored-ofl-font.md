# PDF rendering uses pdfmake with a vendored OFL font, and Markdown is derived

Ticket #24 of spec #20 adds `packages/documents/src/render/`: structured resume and letter content (zod, `content.ts`), `renderResumePdf` and `renderLetterPdf` (pdfmake, `pdf.ts`) and `resumeMarkdown` and `letterMarkdown` (`markdown.ts`). No tables and no MCP tools: the packet ticket stores the content and calls these.

The layout is data in one place (one document definition per kind). Each render returns the PDF bytes, the page count and an over-cap flag (resume over 2 pages, letter over 1). Content is never cut: a long resume renders in full and the caller trims. The page count comes from pdfmake's footer callback, which is the one place it reports the final count; no PDF parsing in production code. Markdown is derived from the same validated content, never stored apart from it, so the two cannot drift.

Work experiences are drawn newest first by the renderer (current roles first, then end month, then start month), whatever order the content arrives in, because the spec fixes the German CV order. The skill may still choose which experiences to include by relevance; only the drawing order is fixed. Dates are `YYYY-MM` and `YYYY-MM-DD` strings; a null end month means current. Headings follow `locale` (de or en), so the documents stay in the language of the master documents and nothing is translated.

The font is Roboto 3.016, copied unmodified into `packages/documents/fonts/` (Regular, and Medium drawn as bold) with the licence text. The spec assumed Apache 2.0; the font file's own name table says SIL Open Font License 1.1 (the pdfmake package is MIT, the font inside it is OFL). OFL permits bundling with software when the notice and licence travel with the files, which `fonts/OFL.txt` and `fonts/README.md` do. The font is vendored rather than read from pdfmake's folder so that the licence note sits next to the file we ship and an upgrade of pdfmake cannot change the font under us. A test renders umlauts and the sharp s and reads them back from the PDF.

pdfmake is configured to read only the font folder from disk and never to fetch a URL; the photo arrives as PNG or JPEG bytes and is embedded as a data URI. The pdfmake instance is process-wide (its font and policy settings are global), which is fine while there is one layout. pdfmake ships no types and the community `@types/pdfmake` references the DOM lib, which changes the types of `fetch` for the whole repo (it broke the typecheck of an unrelated API test), so `src/render/pdfmake.d.ts` declares only the part of the API the renderer uses. The same reason keeps pdfjs-dist out of the typecheck: the test helper loads it by a variable specifier and types the three calls it needs. Tests extract text with pdfjs-dist (dev dependency) and count pages, as the spec's Seam 3 says.
