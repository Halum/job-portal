# Job automation

Search and tracking system for job postings: sources are polled on a schedule, postings are deduplicated and scored against the user's Targets, and everything is driven through an MCP endpoint. Spec: GitHub issue #3. This repo is public: no personal data, no real search criteria, no secrets.

## Branches

`main-automation` (orphan, shares no history with `main`) and `develop-automation`. Feature branches come from `develop-automation` as `feature/*`. The old Job Portal on `main`/`develop` is never touched. No deploy workflow exists here.

## Commands

- `pnpm install`, then `docker compose up -d` and `cp .env.example .env`
- `pnpm dev:api` (MCP at http://localhost:3000/mcp), `pnpm dev:worker` (both load `.env` through `tsx --env-file-if-exists=.env`; without it `loadConfig` fails with ConfigError, because it reads only `process.env`)
- `pnpm typecheck`, `pnpm lint`, `pnpm format:check`
- `pnpm test:fast` (unit only), `pnpm test` (adds Testcontainers integration, needs Docker), `pnpm test:coverage` (CI gate)
- `pnpm db:generate` after changing a module schema
- `pnpm smoke`: manual live check, one cycle against the real sources and the configured runner (reads `.env`, sends no digest, refuses when NODE_ENV=test or CI is set, never in CI)
- Claude skill: `skills/job-hunter/SKILL.md`; link it into the user's skills with `ln -s "$(pwd)/skills/job-hunter" ~/.claude/skills/job-hunter`

## Hard rules

- TypeScript strict, no `any`. ESLint strict. Never use the em dash character.
- Each domain module is a package with its own Postgres schema and its own Drizzle migrations. A module never queries another module's schema; it calls that module's interface.
- Secrets and the user's real details come from env only. Never commit `.env`.
- Numeric settings: null means unset, never a falsy check (`0` is a valid value).
- Tests drive public interfaces. Integration tests use real Postgres and Redis through Testcontainers; nothing hits the network. Name them `*.integration.test.ts`.
- Coverage gate: statements, lines, functions 80%, branches 70%.
- Hooks are per worktree: `pnpm install` runs `scripts/prepare-hooks.sh`, which sets `core.hooksPath` with `git config --worktree` (never the shared `.git/config`). Run it in every new worktree.
- Pre-commit runs typecheck, lint, fast tests, and gitleaks, osv-scanner, semgrep when installed. CI runs all of them.
- Agent decisions are in `docs/adr/agent/`.
- Terms in `GLOSSARY.md` name things in code, database, tests and issues.

## Architecture map

- `packages/shared`: logger.
- `packages/config`: zod-validated env config (`loadConfig`).
- `packages/db`: Drizzle on postgres.js client and `runMigrationsWithLock` (advisory lock, one tracking table per module in schema `drizzle`).
- `packages/accounts`: schema `accounts`, users table, seed, constant-time bearer token check (`MCP_BEARER_TOKEN`).
- `packages/discovery`: schema `discovery`: Postings (unique per user, source, source posting id) and Jobs (one or more Postings each, merged by unique per-user company key or URL key, `src/keys.ts`; ADR 0006). Source interface, the Bundesagentur and bambase sources (`src/sources/`, recorded fixtures in `src/sources/fixtures/`), `poll` (returns the Jobs of new Postings), `listJobs` (optional `jobIds` restriction applied before paging), `listMatchable`, `getJob`, `addJob`, `splitJob`, and AI merge (`createAiMerge` in `src/ai-merge.ts`: `run` asks the AI about near matches and merge conflicts and raises ai_merge Review items, `apply` merges a confirmed one; Jobs have `merged_into`, table `merge_checks`; ADR 0013). The Greenhouse, Lever and Ashby sources (`sources/ats.ts`, one `createAtsSource` per ATS over the directory's marked boards; a failing board is one error line, not a failed run) and `createRateLimitedFetch` (requests per host, `BOARD_REQUESTS_PER_SECOND`; slots in memory or shared through Redis with `createRedisSlots`, ADR 0010). `resolveBoardUrl` recognises a careers URL and `fetchBoardPostings` refuses an unsafe board id.
- `packages/matching`: schema `matching`: Global defaults, Targets (unique per user and name, pausable) and `candidates` (Jobs that passed a Target's hard filters and prerank). Criteria are one zod schema with every field nullable (null inherits; 0 and false are real values; `goneColdDays` is a Global-default-only setting), `resolveCriteria` is pure. `run` is hard filters (exclusion words, blocked companies, remote, radius from the bundled GeoNames table in `data/`, CC BY 4.0) then prerank per Target; `searchQueries` feeds the Bundesagentur source; `listJobIds` (with `minScore`) backs list_jobs by Target, `listNewTags` feeds the Digest. `score` is the AI fit score per candidate (`src/scoring.ts`: prompt, answer parser, language judged in code; table `scores`; candidates claimed with `FOR UPDATE SKIP LOCKED`), `listScores` backs get_job (ADR 0011). It reads Jobs only through injected `loadJobs` and `hasApplication` (ADR 0009).
- `packages/boards`: schema `boards`: the Board directory (shared, no user id): `importBoards` (idempotent), `listMarked`, `markBoards` (marks boards that posted in Germany or remote EU, touches only the mark), the per-user Watchlist (`createWatchlist`: `add`, `remove`, `list`, `addMarkedBoard`, and `listBoards`, which narrows the marked boards when the Watchlist is not empty; ADR 0010), bundled JobSync company lists in `data/` (MIT, `data/NOTICE.md`), ADR 0008. `pnpm --filter @job-portal/worker boards:import` and `boards:mark` run the scripts.
- `packages/ai`: schema `ai`: the AI runner interface (`AiRunner`, `AiError` with a class) with OpenRouter (HTTP) and `claude -p` (child process, prompt on stdin) implementations, `createAi(log, runner).run` (parses the answer, logs every call, rethrows failures) and `createAiLog` (`totals`, `recent`). The fake claude binary for tests is `packages/ai/test-fixtures/fake-claude.mjs`. ADR 0011.
- `packages/review`: schema `review`: Review items (kind ai_merge / ai_fit_rejection / mail_match, subject ids, model, status pending / confirmed / disagreed; unique per user, kind and subject) with `create` (optional caller transaction), `list`, `decide` (row lock, then the caller's applier in the same transaction, then the decision) and `stats` (agreement per kind and model, survivors). It imports no other domain module; the creating module applies its items (ADR 0012). Matching raises ai_fit_rejection items and applies them (`applyFitRejection`, table `tag_overrides`); Discovery raises and applies ai_merge items; `exists` and `mergeSubject` support it.
- `packages/pipeline`: schema `pipeline`: Runs (counts incl. `prerankPassed`, `scored`, `tagged`, `aiRejections`, `aiMergeItems`, `aiCalls`, `aiCostUsd`; after Matching a Run runs the optional `aiMerge` dependency and then scores every unscored candidate through the optional `scoring` dependency, then calls the optional `notifications` dependency last (`observeFailures` turns the stable error lines of Discovery boards and Matching AI classes into failure types `source:<id>`, `board:<ats>:<token>`, `ai:<runner>:<class>`, named by `aiRunnerName`; a crash there is an error line, ADR 0014); status running / completed / completed_with_errors / failed). `execute` polls one source through Discovery; the database allows one running run per user and source; a run still running after `staleAfterMs` (default one hour) counts as lost: the next `execute` for that source and the sweep on worker start (`failStaleRuns`) fail it, and never touch a fresh run, so several workers can share a database.
- `packages/notifications`: schema `notifications`: the outbox (`messages`: digest, alert and line, stored before sent; `sendLines` stores short status lines such as Gone cold and Gmail status changes; `setFailure` opens or closes one failure type such as `gmail_token` outside a run), `afterRun` (called last by the Pipeline: opens and closes failure types, stores one Digest of the (Job, Target) pairs not yet listed with unsent digests folded in, sends pending messages through the n8n webhook, alerts first, with bounded retries and backoff), `digest_pairs` (a pair is listed once ever) and `open_failures` (alert once on start and once on recovery). It also keeps a per-user `watermarks` row (new tags are looked up from it, and it moves only once a digest is stored). A digest over 3900 characters is split into several outbox rows, each sent and counted on its own. It reads other modules only through injected functions wired in `buildNotifications` (`apps/worker/src/notifications.ts`). `NOTIFY_WEBHOOK_URL` and `NOTIFY_TOPIC_ID` are env only; unset skips the step. ADR 0014.
- `packages/tracker`: schema `tracker`: application status, furthest stage, applied and apply-by dates, Timeline events and notes. The only writer of any state change, including the discovery state on the Job row: one transaction takes the Job row lock through Discovery, checks `src/model.ts` (transition table), writes the event (ADR 0007). `setDiscoveryState`, `setApplicationStatus`, `undoLastChange`, `addNote`, `getTimeline`, `getStates`, `findJobIds`, `goneCold` (the daily check: moves silent applications to Gone cold under the Job lock, calendar days in the user's timezone; ADR 0015).
- `packages/mail`: schema `mail`: the Gmail poll (`createMail(...).poll`: `createGmailClient` over `fetch`, read-only OAuth refresh token, one lease per user), candidate narrowing by sender domain, company name and ATS senders (`src/text.ts`), the AI classifier (`src/classify.ts`, feature `mail_classify`), the processed-mail ledger claimed in the same transaction as the Timeline event (the Tracker takes an optional caller transaction), unmatched mails (`listUnmatched`) and the pending detail of mail_match items (`getMatch`, `applyMatch`). A fake Gmail server for tests is exported as `@job-portal/mail/testing`. ADR 0016.
- `packages/migrations`: `allMigrations`, the one ordered list of every module's migrations (api, worker and tests apply it).
- `apps/api`: stateless Streamable HTTP MCP endpoint at `/mcp`, bearer auth, tools `whoami`, `list_jobs` (filters apply before paging, also by `targetId`), `get_job`, `add_job`, `split_job`, `set_status`, `undo_last_change`, `add_note`, `list_targets`, `upsert_target` (rematches that Target over all stored Jobs), `get_global_defaults`, `update_global_defaults`, `get_run_history` (`src/tools.ts`), `get_watchlist`, `update_watchlist`, `add_board` (`src/board-tools.ts`), `list_reviews`, `decide_review`, `review_stats` (`src/review-tools.ts`; the applier by kind covers ai_fit_rejection, ai_merge and mail_match), `list_unmatched_mails` (`src/mail-tools.ts`; `decide_review` takes an optional `jobId` for mail_match, one of the item's `possibleJobIds`). `get_run_history` includes `errorCount`, per-run AI counts and `aiTotals`; `list_jobs` takes `minScore` and `tagged` with `targetId` (the tag is derived from score and current threshold); `get_job` includes per-Target `scores`. Package entry exports `createApiServer`, so the worker's end-to-end test depends on `@job-portal/api` explicitly. Migrates and seeds on start; it never polls (Sources run only in the worker).
- `apps/worker`: migrates, seeds, marks stale runs failed, then schedules one BullMQ Job Scheduler per configured source (scheduler id = source id) and runs each tick through the Pipeline. When `AI_RUNNER` is set it builds the runner (OpenRouter or `claude -p`, never both), `createAi` with the call log, hands it to Matching (`maxCallsPerPass` from `AI_MAX_CALLS_PER_RUN`) and wires `scoring` and `aiMerge` (`AI_MERGE_JACCARD`, `AI_MERGE_MAX_CALLS_PER_RUN`) into the Pipeline; unset means nothing is scored or merge-checked. When `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET` and `GMAIL_REFRESH_TOKEN` are set (and an AI runner) it also schedules the mail poll (scheduler id `mail`, `GMAIL_INTERVAL_MINUTES`, `GMAIL_START_DATE`, `AI_MAIL_MAX_CALLS_PER_RUN`); unset skips it with one log line. When `NOTIFY_WEBHOOK_URL` and `NOTIFY_TOPIC_ID` are set it builds Notifications (`buildNotifications`, wiring Matching `listNewTags`, Discovery `getJob` and Review `countPending`) and hands it to the Pipeline; unset means the step is skipped with one log line. A daily Gone cold scheduler (`GONE_COLD_INTERVAL_MINUTES`, default 1440; `src/gone-cold.ts` reads `goneColdDays` from the Global defaults, calls Tracker `goneCold`, sends one line per Job through Notifications; ADR 0015). The ATS sources (`src/sources.ts`) fetch the marked directory boards narrowed by the user's Watchlist (empty Watchlist means all marked boards, for every ATS), paced per host through Redis with `connectRateLimiter` (shared with the API and `boards:mark`; a down Redis fails the request, never sends it unpaced). `src/compose.ts` (`composeApp`) wires every module from the config and is shared by `main.ts`, the smoke run (`src/smoke.ts`) and the end-to-end test; its optional `fetch` replaces the whole network. `src/e2e.integration.test.ts` runs the worker cycle (two sources, one rule merge, score, digest, Gmail reply) against fakes and checks it through the real MCP endpoint, and fails when `skills/job-hunter/SKILL.md` misses a registered tool; `src/tracer.integration.test.ts` is the first tracer bullet through MCP.

Packages export TypeScript source directly (no build step); processes run with `tsx`.
